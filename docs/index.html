The headline

The blocker is almost never the API. It is permission.

Only 3 of 100 apps lack a usable API surface. Everything else that cannot be built today is blocked by a human process — an app review, a partner programme, a licence, a plan. That changes what the work is: less reverse-engineering, more queueing.

01

Two thirds are open, but "open" is not "easy"

69 of 100 let a developer mint credentials alone (52 free, 17 on a trial). Self-serve is not the same as a clean build, though: 15 of those 69 still carry a caveat or worse, usually one that only bites at multi-tenant scale.

02

Auth method predicts nothing

OAuth2 dominates (68 of 100) and feels like the "enterprise" signal, but 68% of OAuth2 apps are self-serve versus 72% of the rest — statistically the same. The gate is the approval workflow behind the client ID, not the protocol.

03

App review is the single most common blocker

15 of the 44 non-trivial apps are held up by review or verification; 10 more by a partner, sales or licence gate. Only 3 are blocked by genuinely missing documentation.

04

MCP is already table stakes

72 apps ship a vendor-operated MCP server and 17 more have a community one — 88 of 89 cited endpoints resolved under machine check. The interesting gap is no longer "does an MCP exist" but whether it covers the write paths a toolkit needs.

05

Category is destiny

Developer infrastructure is 8/10 buildable today. Finance is 3/10 and Ecommerce 4/10. Anywhere money or ad spend moves, someone reviews you first.

06

Where the easy wins are

42 apps are build-now and have a broad API surface — the widest tool coverage per unit of effort. The outreach list is short and specific: 7 apps need a human to make contact before any code is worth writing.

The agent

What ran, and where a human was needed

Ten researcher agents, one per category, each holding a category-specific brief about the traps in its own vertical. That brief — not re-prompting — is where most of the accuracy comes from. Then four checks, three of them deterministic code rather than another model's opinion.

1 · Research10 agents × 10 apps, web search, strict JSON schema, honesty rules that make "no public API" a valid answer.agent/research_agent.py
2 · Link checkEvery one of the 385 evidence URLs fetched. Separates genuinely dead links from bot-blocked ones with a second browser-header pass.check_links.py
3 · MCP checkEach MCP claim must resolve on a vendor-controlled domain. Catches the confident claim with nothing behind it.check_mcp.py
4 · Blind re-research20-app stratified sample, re-researched by agents that never saw pass 1 and must quote the vendor page.verify_blind.py
5 · Score & adjudicateDeterministic diff, then every disagreement ruled on against primary sources.score.py · apply_adjudications.py

Where a human was needed

  • Writing the rubric, twice. The first taxonomy was too loose. Most pass-1/pass-2 disagreement was definitional, not factual, so the definitions had to be tightened by hand and the sample re-ruled.
  • Ruling on the 28 disagreements. Deciding that Composio ships multi-tenant toolkits — so Gorgias counts as caveated even though a single-tenant API key is trivial — is a product call, not a lookup.
  • Catching inherited marketing copy. An agent read "APIs and SDKs" on a homepage as an API surface. A human noticed the domain redirect that explained it.
  • Knowing which claims deserve a machine check. "72 official MCP servers" is the kind of headline that must not be wrong, so it got its own verifier.

Honest notes on the build

  • The shipped dataset was produced by the prompts and loops in this repo, orchestrated through Claude Code's subagent runtime. research_agent.py packages the identical loop to run standalone against the Anthropic API.
  • Stages 2, 3 and 5 are plain Python. The accuracy figures are not a model grading itself.
  • Not run: composio_coverage.py joins these 100 against Composio's live toolkit catalog to produce a build queue. The catalog needs an API key (it returns 401 without one) and no key was available, so that panel is absent rather than guessed.
  • 39 records carry medium confidence and 3 low. Those are marked in the data, not hidden.

The verification

How accuracy moved, and what it got wrong

A stratified sample of 20 (two per category, fixed seed) was re-researched blind. Agreement is measured across five fields per app — 100 independent decisions.

57.0%Pass 1, exact agreement with the blind pass
72.0%Counting partial matches on multi-value fields
83.0%Pass 1 answers that survived adjudication
17Corrections applied to the shipped data

The gap between 57% and 83% is the interesting part. Of 28 disagreements, pass 1 was outright wrong 17 times, right 7 times — the blind verifier is not automatically the better agent — and 4 were rubric ambiguity rather than error. The dominant failure mode was not hallucination. It was an under-specified rubric.

Machine checks

  • 382 of 385 evidence URLs resolve (99.2%). 3 were dead and are listed below. A further 11 returned 4xx to a bare client but are live in a browser — counted as live, not as misses.
  • 88 of 89 MCP endpoints resolved. One claim (WhatsApp Business) had no URL at all: it traces to a one-day-old press report of a Meta announcement, and the WhatsApp docs do not mention MCP. Kept, flagged unverified.
  • All 100 records are schema-valid and ID-complete; the pipeline asserts this on every run.

The 3 fabricated-looking links

Plausible URLs on the right domain that do not exist — the exact failure a link checker is for. All three were traced to the real page and corrected.

  • 45 · https://developer.adobe.com/commerce/webapi/get-started/authentica
    Trailing slash 404s on Adobe's docs router; canonical path has no trailing slash.
  • 65 · https://supabase.com/docs/reference/api/management-api
    Agent guessed a plausible-but-nonexistent slug. Real Management API reference lives at /reference/api/introduction.
  • 66 · https://neo4j.com/docs/aura/platform/api/authentication/
    Agent inserted a '/platform' segment that does not exist in the Aura API docs tree.

Honesty

Where this defeated us

Paygent Connect — we could not confirm the product exists

Two independent passes searched for "Paygent Connect (NMI-powered)" and found three unrelated companies: paygent.ai (payment-cost analysis, explicitly never moves money), paygent.co.jp (a Japanese PSP) and paygent.tech (agent virtual cards, whose /docs 404s). No NMI relationship was confirmed anywhere. Recorded as not buildable with no evidence URL, because inventing one would be worse.

fanbasis — pass 1 read marketing copy as an API

It reported REST, SDKs, webhooks and API-key auth. In fact fanbasis.com redirects to commas.com — the company rebranded — and the "APIs and SDKs" line is homepage marketing with no developer docs, portal or key issuance behind it. The blind pass caught it; a hand-run redirect trace confirmed it. This is the clearest single miss in the set.

NotebookLM — pass 1 was too pessimistic

It concluded there was no API and marked it needs-outreach. There is one: Gemini Notebook Enterprise exposes notebook endpoints on Discovery Engine v1alpha with a gcloud bearer token, verified by hand. Consumer NotebookLM still has none. Errors run in both directions.
